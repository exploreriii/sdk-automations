# 6.1 Installation and authentication

**Question this can falsify:** that a selected-repository App installation
gives the platform a stable identity, predictable short-lived tokens, and
diagnosable permission failures.

## Setup

- Throwaway App created on a personal account, webhook pointed at the
  harness tunnel. Permissions: Issues RW, Pull requests RW, Contents R,
  Metadata R — **deliberately omitting** one permission a later step
  needs (Checks R), so the diagnostics case is real.
- Sandbox repository seeded via `harness/` (issues, labels, one PR).

## Steps

1. Install the App on the sandbox as **selected repositories**. Record
   the installation id and the `installation.created` delivery.
2. Mint an installation token via the App JWT. Record TTL from
   `expires_at`, and the token's reported `permissions` and
   `repository_selection`.
3. Use the token until expiry; record the exact failure shape of the
   first call after expiry, then refresh and confirm recovery.
4. Call an endpoint requiring the omitted permission. Record status,
   `x-accepted-github-permissions` header, and body verbatim — this is
   the template for permission diagnostics.
5. Suspend the installation from settings mid-run. Record the failure
   shape of in-flight and subsequent calls, and any delivery received.
6. Unsuspend; confirm recovery without re-installation.
7. Uninstall. Record the terminal delivery and the behavior of a token
   minted before uninstall.

## Observations

- **2026-07-23 — step 1 complete.** `installation.created` captured
  (delivery `eef7a320-86c2-11f1-8991-afa329dc8822`, citation
  `2026-07-23T18-22-30-751Z#2`). Installation id `148563067`, app id
  `4377258`, `repository_selection: "selected"` with exactly the
  sandbox. Granted permissions match the design intent verbatim —
  `issues: write, pull_requests: write, contents: read, metadata: read`
  — with **checks absent** as required for step 4, and all five
  subscribed events present. Installation events arrive without any
  event subscription, as expected.
- **2026-07-23 — step 2 complete.** Token minted; TTL exactly one hour
  (`expires_at` 19:34:52Z for a 18:34:52Z mint), grants and
  `repository_selection: "selected"` confirmed (citation
  `2026-07-23T18-34-51-975Z#1`).
- **2026-07-23 — step 3 complete, expectation falsified
  (FINDING(token-expiry-indistinguishable)).** A saved token probed
  11 min past `expires_at` returned 401 `"Bad credentials"` —
  byte-identical to a wrong-key 401, with no expiry marker in body or
  headers. Expiry is therefore detectable **only from local state**
  (the `expires_at` returned at mint). The adapter consequence is now
  encoded in `packages/core/src/github/failures.ts`: 401 classification takes a
  `tokenPastExpiry` input; the response alone can never say "refresh
  me". Incidentally: the same token probed 2 min *before* expiry
  returned 200 — the TTL boundary is sharp, with no early-revocation
  grace.
- **2026-07-23 — step 4: FINDING(public-repo-permission-bypass).** The
  deliberately-unpermissioned read (`GET …/check-runs`) returned **200,
  not 403** (citation `…#4`). The sandbox is public, and GitHub does not
  enforce App permission grants on reads of publicly visible data; the
  `x-accepted-github-permissions: checks=read` header appears even on
  the success. **Consequence:** missing-permission diagnostics via
  403-plus-header work only for *writes* and *private-repo reads* — a
  read probe on a public repository proves nothing about grants. The
  failure-catalogue row must be re-captured with a write endpoint (or
  after 6.6 flips the sandbox private). Feeds the platform's
  permission-diagnostics design directly.
- **2026-07-23 — step 4 counterpart complete (sandbox flipped
  private).** The identical probe now fails correctly: **403**,
  body *"Resource not accessible by integration"* with a docs link,
  header `x-accepted-github-permissions: checks=read` (citation
  `2026-07-23T18-40-40-043Z#3`). The public/private contrast pair is
  the failure-catalogue entry: same endpoint, same grants, opposite
  outcomes — visibility, not permissions, decided the public case.
  Incidental: the visibility flip needed **no re-installation or
  re-consent**; the permitted baseline read worked immediately after
  (citation `…#2`).
- **2026-07-23 — steps 5–6 complete.** While suspended: 403 with body
  *"This GitHub App installation is currently suspended"* and **no**
  `x-accepted-github-permissions` header (citation
  `2026-07-23T18-46-45-624Z#5`) — so *suspended* and
  *permission-missing* are distinguishable by both body text and header
  presence. `installation.suspend` / `unsuspend` deliveries both
  captured (18:47:10 / 18:47:49). A post-unsuspend call with a fresh
  token succeeded with no re-installation (citation
  `2026-07-23T18-49-30-656Z#2`). Operator note with evidentiary value:
  the run's own step-6 call fired **10 s before** the unsuspend
  registered and correctly still failed suspended (citation `…#6`) —
  suspension state is evaluated per-request, and human-in-the-loop
  timing must be checked against delivery timestamps before reading a
  result.
- **Remaining for 6.1:** step 3's expiry shape (mint-and-hold a token
  past its 1 h TTL, then replay), and step 7 (uninstall), which is
  sequenced after every other experiment because it destroys the
  installation. Whether a *pre-suspension* token revives on unsuspend
  is also untested — only a fresh token was proven.
