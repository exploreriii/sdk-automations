# 6.11 Review facts, issue fields, marker labels and team mentions

The reviews design (`design/guides/capabilities/reviews.md`) rests on four beliefs about GitHub
that no test can hold and no matrix row yet cites. Each is one call, and the session takes an
hour. Nothing below is built until the answers are in.

## Questions

1. **Fields on the closing issues, and the decision on the pull request.** Does the App's
   installation token answer `reviewDecision`, `issueType { name }` and `issueFieldValues` on the
   `closingIssuesReferences` query the sweep already sends (protocol 6.8), and under which grant?
   Is `reviewDecision` null where no rule requires review, `REVIEW_REQUIRED` under a rule, and
   `APPROVED` once satisfied? Does a pull request carry issue fields of its own (expected: none)?
2. **A field edit's webhook.** When the Priority value on an issue changes, does a webhook arrive,
   on which event and action, and does the payload carry the new value?
3. **A missing label on add.** Does `POST /repos/{o}/{r}/issues/{n}/labels` with a name the
   repository lacks create it, or refuse? The documentation does not say. If it refuses, does
   `POST /repos/{o}/{r}/labels` create it under Issues W?
4. **A team mention from the App.** Does a comment the App posts mentioning `@org/team` notify the
   team's members? This one needs an organization sandbox with a team of two accounts — a personal
   repository has no teams — and it gates every `notify` on the page, not only the community one.

Alongside 1, at no extra cost: on the reviews list the sweep already reads, the
`author_association` and `state` of a single inline comment by the lead (expected `OWNER`,
`COMMENTED`) and by a second, unaffiliated account (expected `NONE` or `CONTRIBUTOR`).

## Red line

The lead's personal sandbox for 1–3; a throwaway organization sandbox for 4, never a Hiero
repository (P8, D22). Every write App-authored and reversed by the lead as a human before the
protocol closes: labels removed, the branch rule deleted, comments left as evidence. One request per
case — a retry replaces the failure shape this protocol exists to observe. The disposable runner
lives in ignored `harness/`, raw responses in ignored `evidence/`; never an authorization header,
token, JWT or private key.

## Method

| Fixture | State | Made by |
|---|---|---|
| issue A | Priority `Urgent`, type `Bug` | the lead, in the sandbox's issue fields |
| issue B | no priority, type `Feature` | the lead |
| pull request P1 | closes A and B (`Closes #A`, `Closes #B`), open, not a draft | the lead |
| pull request P2 | base branch with a rule requiring one approval; no review yet | the lead |
| a second account | unaffiliated with the sandbox | the lead's alternate |
| organization sandbox | one repository, one team of two accounts, the App installed | the lead |

Question 1, one GraphQL call per case, `pageInfo` followed as in 6.8:

```graphql
query ReviewFactsProbe($owner: String!, $repo: String!, $number: Int!) {
  repository(owner: $owner, name: $repo) {
    pullRequest(number: $number) {
      reviewDecision
      closingIssuesReferences(first: 100, excludeUserLinked: true) {
        nodes {
          number
          issueType { name }
          issueFieldValues(first: 25) {
            nodes {
              ... on IssueFieldSingleSelectValue { field { ... on IssueFieldCommon { name } } value { name } }
            }
          }
        }
      }
    }
  }
}
```

Cases: P1 (expected: decision null, A's field and type, B's type); P2 before any review
(`REVIEW_REQUIRED`), after the lead approves (`APPROVED`); P2 with the second account's approval
alone (still `REVIEW_REQUIRED` — GitHub counts it for nothing). Record the grant level the token
holds and whether `issueFieldValues` answers or errors under it; if it errors, repeat with Issues R
raised to the next grant and record which one answers.

Question 2: with the capture receiver of protocol 7.1 running, change A's Priority to `High`, then
clear it. Record the events received, their actions, and whether the field appears in the payload.

Question 3: `POST .../issues/{P1}/labels` with `["community review welcome"]`, a name the sandbox
lacks. Record the status, the response body, and the repository's labels afterwards. If refused,
`POST /repos/{o}/{r}/labels` with the same name, then repeat the add. Remove the label by hand.

Question 4: in the organization sandbox, post one comment through the App on an open issue whose
body begins `@<org>/<team> — probe 6.11`, with both team members subscribed to nothing. Record
whether each member's notification inbox shows it within five minutes, and whether the team is
visible or secret.
