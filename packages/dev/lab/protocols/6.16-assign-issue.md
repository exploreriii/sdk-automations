# 6.16 Assign one login to an issue

## Question

Can the App put one named login on an issue's assignees with `issues:write`, does the issue read
show it immediately, is a repeated call safe, and what does GitHub answer for a login it cannot
assign? The last answer decides how the adapter proves an assignment landed.

This closes the missing endpoint row behind assignment's `assign` operation. The release half,
`DELETE …/assignees`, was confirmed for inactivity's release and is re-measured here only so
assignment's `unassign` can reuse that row.

## Red line

A new issue in a personal, private sandbox repository only, created for this run and closed after
it. The only login assigned is the sandbox owner's; the two refused logins are a real account with
no access to the repository and a name no account holds. No contributor issue or Hiero repository
is used. The shell is stopped for the run, so no capability reacts to the App's own deliveries.

## Method

Use one installation token with `issues:write`, minted from the App's key. Record the status,
remaining primary quota, and the issue's `assignees` after each step.

1. Read `GET /repos/{owner}/{repo}/issues/{number}`. Require `assignees: []`.
2. Ask `GET /repos/{owner}/{repo}/assignees/{login}` for the owner and for the stranger.
3. Send `POST /repos/{owner}/{repo}/issues/{number}/assignees` with `{ "assignees": [owner] }`.
4. Read the issue immediately and two seconds later. Require the owner in `assignees` both times.
5. Send the same `POST` again.
6. Send the `POST` naming the stranger, then naming a login that does not exist.
7. Read the issue. Record whether either login appears.
8. Send `DELETE /repos/{owner}/{repo}/issues/{number}/assignees` with `{ "assignees": [owner] }`.
9. Read the issue immediately and two seconds later. Require `assignees: []` both times.
10. Send the same `DELETE` again.
11. Read the timeline and record the actor of the `assigned` and `unassigned` entries.
12. Close the fixture.

## Expected result

GitHub documents `POST …/assignees` as `201`, and says logins without permission to be assigned are
ignored silently. If that holds, a `201` proves nothing on its own: the adapter must prove an
assignment by reading the item's `assignees` back, never by the status.

## Result — 2026-10-07

Run with App `5229146`, installation `169012723`, against disposable issue
`danielmarv/automation-sandbox#6`, approved by the sandbox owner.

- The initial read returned `assignees: []`. The assignable check answered 204 for the owner and 404
  for the stranger.
- Assigning the owner returned 201 with the owner in the response. Reads immediately and two seconds
  later named the owner.
- Repeating it returned 201, the list unchanged.
- **Assigning the stranger returned 201, and so did assigning a login that does not exist.**
  Neither appeared in the response or in the read that followed. The status cannot tell an
  assignment from a refusal; only the read-back can.
- Releasing the owner returned 200 with `assignees: []`. Reads immediately and two seconds later
  were empty. Repeating it returned 200.
- Each call cost one primary-quota request.
- **Both timeline entries named the App's bot as actor, `type: Bot`**: `assigned danielmarv by
  danielmarv-automation-sandbox[bot]` and the matching `unassigned`. The release row in the
  endpoint matrix records the opposite for an App-made release on 2026-09-12 — the assignee as its
  own actor. This run does not explain the difference, so the ordering read keeps treating an
  `unassigned` entry by the assignee as possibly the App's own.
- Cleanup closed the fixture with no assignee.

Confirmed by `2026-10-07T21-25-58-555Z#1–16`.

## A claim by someone with no access

On a Hiero repository the person typing `/assign` is usually neither a collaborator nor the owner,
so this part decides whether assignment works where it is meant to. GitHub documents that anyone
who has commented on an issue can be assigned to it; the run above saw only the owner assigned and a
stranger declined.

### Method

A public sandbox repository, separate from the private one, with the App installed on it alone
beside the private sandbox; the labels mapped as there; `mode: active` with `assignment` enabled;
one issue carrying `ready`. A second account with no access to the repository. The shell from this
checkout with writes armed, behind the relay.

1. Ask `GET /repos/{owner}/{repo}/assignees/{second}` before the account has commented.
2. From the second account, comment `/assign` on the ready issue.
3. Record the shell's decision and GitHub's issue.
4. Ask the assignable check again.
5. If the claim was declined, send `POST …/assignees` naming the second account with the App's
   token, to tell GitHub's rule from the App's grant.
6. From the second account, comment `/unassign`. Record the release and its notice.
7. Close the issue.

### Result — 2026-10-07

Run with App `5229146`, installation `169012723` — narrowed to the two sandboxes before the run —
against `danielmarv/automation-sandbox-public#1`, and the second account `joshicmarvin`, approved by
the sandbox owner. The account was confirmed to be no collaborator (404) and to have no comment on
the issue.

- **Before commenting, the assignable check answered 404**; the owner's answered 204.
- `joshicmarvin` commented `/assign` at 22:15:57. The shell assigned him — the timeline reads
  `assigned joshicmarvin by danielmarv-automation-sandbox[bot]` at 22:16:04 — the assignee read
  named him, and only then was the claim notice posted. One effect, two landed calls, no refusal.
- **After commenting, the assignable check still answered 404**, though the assignment had just
  landed. The check does not know the commenter rule, so it cannot predict a claim; the read-back
  after the write is the only proof, as the first run concluded for other reasons.
- Step 5 was not needed.
- `joshicmarvin` commented `/unassign` at 22:17:24. The release went through the release endpoint
  (`unassigned … by danielmarv-automation-sandbox[bot]`, 22:17:29), the read showed him gone, and the
  same comment was rewritten to the release notice. Two landed calls.
- The issue was closed with no assignee.

**A contributor with no access to a public repository can claim an issue they have commented on,
and release it.** Commenting `/assign` is itself the comment that makes them assignable, so every
claim satisfies the rule by construction. Evidence: `evidence/2026-10-07T22-15-28Z-6.16-no-access/`.

Still open: a private repository, where a person with no access cannot comment at all, and a
contributor with read access only, which no Hiero repository's claim depends on.
