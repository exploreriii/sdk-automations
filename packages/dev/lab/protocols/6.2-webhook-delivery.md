# 6.2 Webhook delivery

**Question this can falsify:** P9 — that a receiver must durably accept
work before acknowledging — and D1's premise that GitHub's delivery
machinery alone can carry recovery. D18's single-process assumption is
also on trial here.

## Setup

Harness webhook receiver running with **named kill points** (see
`harness/src/webhook.ts`): `before-ack`, `after-ack-before-durable`,
`after-durable`. A scripted issue-labeling action generates deliveries
on demand.

## Steps

1. **Signature rejection** — send a forged delivery (wrong HMAC) and a
   valid one; record both outcomes. The forged one must be rejected
   before any processing.
2. **Fast acknowledgement** — respond 200 immediately, then process;
   separately delay the response past ~10s and record what GitHub does
   with the delivery (timeout classification, retry or not).
3. **Duplicates** — use *Redeliver* on a processed delivery; confirm the
   delivery id (`X-GitHub-Delivery`) is identical and record what a
   dedup check needs.
4. **Out-of-order** — generate two ordered events, redeliver the first
   after the second; record how order is (not) recoverable from headers.
5. **Restart before acceptance** — `kill -9` at `before-ack`; record
   whether GitHub marks the delivery failed and whether it retries
   unprompted.
6. **Restart after acceptance** — `kill -9` at `after-ack-before-durable`;
   this is the loss window P9 predicts. Record that the delivery is
   acknowledged-but-lost.
7. **Reconciliation** — recover the missed event of step 6 using
   `GET /app/hook/deliveries` (30-day retention) and manual redelivery
   via the API. Time the listing cost at realistic volumes.
8. **Bounded queue** — flood ~50 deliveries with processing paused;
   record memory/queue behavior and what a bound must do.

## Observations

- **2026-07-23 — step 1, complete.** An unsigned POST was rejected before
  any processing (401, `rejected-signature`,
  `2026-07-23T18-22-30-751Z#1`); the harder variant — a well-formed
  `sha256=` HMAC computed under the wrong key — was likewise rejected
  with no accept-log entry (`2026-07-23T19-31-23-338Z#1`), exercising
  the constant-time comparison path, not just the header-shape check.
- **2026-07-23 — step 3, incidental evidence (corrected attribution).**
  Every delivery in the first session was accepted **twice with an
  identical delivery id** — 154 unique ids, 308 accepts, gaps 1–196 ms.
  Initially read as GitHub duplicating; investigation found **two
  tunnel forwarders accidentally attached to the same smee channel**,
  each forwarding every delivery once. GitHub itself sent each delivery
  once. Two lessons stand: (1) the *transport* layer can manufacture
  wholesale duplication that GitHub never sees, so dedup must key on
  `X-GitHub-Delivery` regardless of upstream guarantees, and it must
  tolerate near-simultaneous (1 ms) duplicates; (2) attribute before
  concluding — the first version of this observation blamed the wrong
  layer. GitHub-originated duplicates still to be exercised via
  Redeliver in the formal run.
- **2026-07-23 — step 6 (P9) confirmed.** In `ack-first` mode the harness
  was SIGKILLed at `after-ack-before-durable` on issue-153's delivery.
  GitHub's ledger records that delivery `status: OK, code: 200` — from
  its side the webhook *succeeded* — while the local durable log has no
  trace of issue 153. This is exactly the loss P9 predicts: a receiver
  that acknowledges before durably accepting drops work with no upstream
  signal that anything was lost. **P9 moves from hypothesis to
  demonstrated.** The mirror step 5 (`before-ack` crash, issue 152) is
  the benign case: no ack was sent, so GitHub would mark it failed and
  it is legitimately re-drivable.
- **2026-07-23 — step 7: reconciliation works, with a caveat.** The lost
  issue-153 delivery was found in `GET /app/hook/deliveries` and
  redelivered (`POST …/attempts` → 202); it then arrived and was durably
  accepted (guid `20db79d8…`, redelivery citation
  `2026-07-23T19-04-37-138Z#1`). So the deliveries API *is* a sufficient
  recovery source for a lost delivery — **but only within its ~30-day
  retention, and only if something notices the loss to trigger the
  redelivery.** Nothing in GitHub's ledger flags 153 as needing
  recovery — it reads `OK`. Detection still requires local durable
  state; the API is the repair tool, not the tripwire. Directly informs
  D1 / D24 / D27.
- **2026-07-23 — step 2 + FINDING(transport-masks-ack-semantics).**
  GitHub's ~10 s timeout **cannot be measured through an ack-first
  relay**: with the receiver deliberately holding responses 15 s, the
  ledger still recorded `OK, 0.05 s`, because smee.io acknowledges
  GitHub the moment it receives the delivery, before forwarding.
  The stronger corollary was then demonstrated directly: with the
  tunnel client down, a delivery was recorded `OK` by GitHub while the
  local log never saw it, and reconnecting did not replay it — the
  relay is *structurally* an ack-first receiver, recreating P9's loss
  window at the transport layer with no local crash required. Two
  consequences: (1) any deployment with a relay in the path must treat
  GitHub's `OK` as "reached the relay", never "reached us" — the
  step-7 reconciliation loop is therefore load-bearing even when the
  receiver itself is durable-first (feeds D1/D24/D27); (2) the timeout
  classification itself (does GitHub mark >10 s responses failed, and
  does it retry?) needs a directly-exposed endpoint and remains
  **untested** — recorded here as a scope limit, not a result.
- **2026-07-23 — step 8: no bound exists, so the bound is ours to
  design.** Fifty API redeliveries of one delivery (identical guid,
  all 202) were all durably accepted — reinforcing that dedup must key
  on the delivery guid and tolerate arbitrary repetition. A genuinely
  concurrent burst (50 signed synthetic POSTs fired at once, receiver
  holding every response 15 s) was absorbed whole: all 50 sockets held
  simultaneously, responses spread over 21 ms, RSS unmoved at
  24.5 MB. Nothing in Node or the primitive server pushed back —
  memory cost is linear in payload size × concurrency with no ceiling.
  What a real bound must do, given the other results: cap concurrent
  unacknowledged deliveries; when saturated, *reject fast* (5xx) so
  GitHub's ledger marks the delivery failed and it stays legitimately
  re-drivable, rather than holding acks toward a timeout; and never
  acknowledge what it has not durably accepted (P9). Payloads at this
  size (~1–50 KB) make memory the wrong first worry — the loss
  semantics of an overflowing queue are the design constraint.
- **2026-07-23 — FINDING(delivery-id-precision).** Delivery ids exceed
  2^53 (e.g. `3832900504397021184`); a naive `JSON.parse` silently
  rounded the trailing digits (`…294272` → `…294300`), and a redeliver
  by the corrupted id would 404. The harness now quotes the `id` field
  to a string before parsing. Any component that stores, compares, or
  redelivers by delivery id must treat it as an opaque string — a real
  correctness trap for the platform, not a harness quirk.
