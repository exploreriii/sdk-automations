# 6.3 Configuration

**Question this can falsify:** that the strict, fail-closed configuration
model (D17, D31, Q14) survives contact with real repository states — and
that the `core/` validator's invariants hold against files fetched from
GitHub rather than test fixtures.

The harness parses fetched YAML with the **`core/` validator** — the
pure-logic track's first consumer. Any divergence between a test-fixture
outcome and a fetched-file outcome is itself a finding.

## Steps

For each state, fetch the config as the platform would (Contents API on
the default branch) and record the validator's verdict and resulting mode:

1. **Absent** — no config file. Must land in `observe` (D31).
2. **Valid** — a minimal reviewed config. Must produce exactly the
   enabled capabilities and nothing else.
3. **Invalid** — one bad value. One error must yield *no* configuration
   (`observe`), not a partial one.
4. **Unknown keys** — a plausible-but-unknown key. Must be rejected, not
   ignored (fail closed).
5. **Outdated** — a config referencing a capability/schema no longer
   supported. Record the verdict and the report a maintainer would see.
6. **PR-only change** — a config change existing only on a PR branch.
   The default branch's config must remain the effective one.
7. **Default-branch update** — merge the change; measure how the
   effective config is observed to change (event vs poll; latency).
8. **Dormant settings** — a disabled capability with settings present.
   Settings must be inert but not invalid.
9. **Effective-config report** — for states 1–5, capture what the
   platform can report back about the config it is (not) using.
10. **Missing permission** — a config enabling a capability whose
    permission the App lacks (from 6.1's omitted permission). Record how
    early this is detectable.

## Observations

- **Fail-closed holds against fetched files.** Every invalid state
  (bad value, unknown key, wrong schema version) produced zero
  configuration and `observe`, with single precise errors — identical
  behavior to the `core/` unit fixtures. The pure-logic validator's
  first contact with GitHub-fetched YAML surfaced no divergence.
- **Effective config is event-observable within seconds.** The
  config-commit push delivery arrived **2.78 s** after the write, and
  every one of the session's seven config writes produced a captured
  push delivery. A platform subscribed to `push` can reload config
  event-driven; polling is a fallback, not the mechanism.
- **PR-only changes are inert**, as required: default-branch fetch
  returned the old config while the PR ref showed the new one — the
  fetch-by-ref distinction is the entire enforcement mechanism.
- **FINDING(config-capability-registry-gap).** A config enabling a
  nonexistent capability (`checksGate`) **passes validation** — the
  validator has no capability registry and no permission model
  (settings are contractually opaque, and capability names are
  free-form). Static validation therefore cannot catch: misspelled
  capability names, capabilities the platform doesn't ship, or
  capabilities whose permissions the installation lacks (protocol
  step 10). Earliest detection points, in order: a capability-registry
  check at config load (platform layer, missing from the design), and
  the 6.1 permission probe at installation time. Feeds D23 and the
  effective-config report design.
- **Incidental safety property:** the App's `contents: read` grant
  means the platform *cannot modify its own configuration* — config
  writes went through operator credentials. Worth preserving
  deliberately in the permission ceiling.
