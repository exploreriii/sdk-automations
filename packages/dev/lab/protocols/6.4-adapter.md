# 6.4 Adapter

**Question this can falsify:** D20 — that one adapter can own rate
limits, retries, pacing, and conditional reads behind interfaces narrow
enough that capabilities never see Octokit — and D9's assumption that
timeline reads are affordable. Produces the endpoint-and-permission
matrix (Q16) and the fleet budget inputs (Q10).

## Steps

1. **Pagination** — list the sandbox's ~150 seeded issues; record page
   size behavior, link headers, and total request count.
2. **Conditional reads** — repeat a read with `If-None-Match`; confirm
   304 and record whether it consumes primary quota (compare
   `x-ratelimit-remaining` before/after).
3. **Rate-limit headers** — for every call in the run, harvest
   `x-ratelimit-*` into the evidence log; summarize per-endpoint cost.
4. **Secondary limits** — a *bounded* concurrent write burst (cap: 20)
   until a secondary-limit 403 appears; record the `retry-after` /
   documented backoff signal, then stop. Do not repeat the provocation.
5. **Forbidden operation** — call an endpoint outside the App's grant;
   record the 403 body ("Resource not accessible by integration") for
   the diagnostics catalogue.
6. **Validation error** — one deliberate 422; record the error schema.
7. **Timeouts and backoff** — set an aggressive client timeout, confirm
   the adapter's bounded backoff, and record retry counts.
8. **Timeline read cost (D9)** — read the issue timeline for a busy
   issue; extrapolate the per-sweep cost for a fleet of ~50 repositories
   against the measured budget.

## Observations

- **Uniform pricing, and 304s are free.** Every call in every run cost
  exactly one unit of the 5000/h installation budget regardless of
  endpoint or page size — and conditional reads that come back 304 cost
  zero, three-for-three across runs. The adapter's cheapest request is
  a repeated one: an ETag cache converts steady-state polling of
  unchanged resources into free traffic. This is the single biggest
  lever on the fleet budget (Q10).
- **FINDING(secondary-limit-no-wait-signal).** The content-creation
  secondary limit fired with *no* `retry-after` header and with primary
  quota nearly full — the two signals an adapter would naturally key on
  are both silent. The 403 is distinguishable from the permission 403
  (step 5) only by body text (`secondary rate limit` vs `Resource not
  accessible by integration`), so the diagnostics catalogue must parse
  bodies, not just status codes. Absent a wait signal, backoff length
  is the adapter's own guess; GitHub's docs say "wait at least one
  minute" for content-creation blocks — that documented floor, not any
  header, is what D20's retry policy must encode. Onset was ~71 writes
  at concurrency 20 in ~7 s: any fleet-wide write bursts must be paced
  well below this, or serialized per the docs' at-most-one-concurrent-
  content-write guidance.
- **Timeline reads are cheap enough for D9 — with conditionals.** A
  busy issue's full timeline (80 events, mixed kinds) is one request
  and ~0.5 s. Extrapolating: a sweep of 50 repositories × 20 active
  issues = 1,000 requests ≈ 20% of one hour's budget per sweep — 
  viable but not generous *uncached*. With ETag caching (step 2),
  unchanged issues re-poll for free, so steady-state sweep cost tracks
  the number of *changed* issues, not the fleet size. D9 stands,
  conditional on the adapter actually implementing conditional reads.
- **Error shapes are regular enough for a catalogue.** The three
  failure families seen across 6.1–6.4 (integration-403, validation-422
  with structured `errors[]`, secondary-403 with prose body) are
  mutually distinguishable from body content alone; nothing needed
  guessing. The 422's `errors[]` triple (`resource`, `field`, `code`)
  is precise enough to surface to maintainers verbatim.
- **The plugin caveat is an adapter design input, not a footnote:**
  Octokit's default throttling/retry plugins silently absorb secondary
  limits and transient failures. Fine for a harness convenience — but
  D20's adapter must either own these policies explicitly (disable the
  plugins, implement bounded retry itself) or accept invisible,
  unbounded-by-contract waits inside its dependency.
