# 6.5 Recovery and storage

**The decision experiment.** D1, D13, D24, and D27 are all `reopened` on
the same question: what minimum owned state does recovery actually
require (Q15)? This run produces
[`design/operations/storage-decision.md`](../../../../design/operations/storage-decision.md).

## Setup

Two effects, chosen because the platform's first capabilities need
exactly them:

- **E1** — apply one managed comment (marker + metadata payload, D12).
- **E2** — one reversible mapped-label change.

The harness executes each effect as its real multi-call sequence and
exposes a kill point **after every API call**, plus one special mode:
**lost-response** — the write is sent, GitHub may have accepted it, and
the response is discarded before any local record is written. That is
the worst case D24 must survive.

## Steps

1. Run E1 to completion; record the full call sequence as the baseline.
2. Re-run E1, killing after call 1, then after call 2, … — one run per
   kill point. After each kill, attempt recovery three ways **without
   using process memory**:
   - **(a) GitHub state** — re-read current comments/labels and events;
     decide whether the effect is absent, partial, or complete.
   - **(b) Comment metadata** — parse App-authored comment payloads as
     the write-ahead record (D27's proposal).
   - **(c) Owned store** — a single-file SQLite journal written by the
     harness before each call.
3. Repeat step 2 in lost-response mode. The key question per source:
   can it distinguish "GitHub accepted the write" from "the write never
   happened" without risking a duplicate?
4. Run E2 through the same grid.
5. For each of the five operational needs, judge each source
   **sufficient / insufficient / sufficient-at-cost**:
   delivery deduplication, pending effects, retries, schedules,
   coordination (two workers, one effect — simulate with two harness
   processes).
6. Write the result into `storage-decision.md` with citations.

## Observations

- **No single source suffices; the sufficient pair is (c) detect +
  (a) resolve.** The journal's intent row is the only thing that knows
  work was pending (`#8`: GitHub shows `absent`, identical to
  never-requested) — but after a lost response the journal alone reads
  `SENT-UNKNOWN` (`#14`), and only a re-read of GitHub state resolves
  it. Retrying without that resolution duplicated the comment on the
  first try (`#18`). Recovery = journal to know *what* to check,
  GitHub to learn *how it ended*.
- **Effect idempotency class determines how bad the worst case is.**
  The same lost-response + naive-retry sequence that duplicated E1 was
  harmless for E2 (`#29`) — GitHub makes label-add idempotent.
  Non-idempotent effects (comment creation) are exactly where the
  marker read-back and the journal matter; the capability layer should
  declare each effect's class rather than treat all writes alike.
- **Comment metadata is a receipt, not a WAL.** For E1 the managed
  comment is its own receipt — parseable after every crash that let
  the write land. But it records nothing before the write exists
  (`#8`), covers only comment-shaped effects (E2: no record in any
  state), and GitHub offers no conditional create, so it cannot
  coordinate (`#32` — the naive race *includes* the read-check D27
  would rely on). Extending E2 with a WAL comment would cost +2 writes
  per effect — into the same content-creation secondary limit 6.4
  measured with no warning header.
- **Coordination needs a real lock.** Two workers with full read-check
  logic still duplicated (`#32`); the single-file SQLite claim table
  serialized them with nothing but an `INSERT` on a primary key
  (`#35`). This is the smallest owned-store win: one table, one
  constraint.
- The judgments and the resulting decision are in
