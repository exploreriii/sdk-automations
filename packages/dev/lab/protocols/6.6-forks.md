# 6.6 Fork and private repositories

**Question this can falsify:** that the App's base-repository operations
behave predictably for fork-sourced pull requests — the case every SDK
repository lives in daily.

**Red line (from the build plan):** no step executes fork-provided code
with App write credentials. This protocol reads and labels; it never
runs anything from the fork.

## Setup

- A second personal account forks the sandbox (public fork).
- The sandbox is then made private and re-forked internally, repeating
  the grid for the private case.
- One PR from each fork into the sandbox.

## Steps

For each fork type (public, private):

1. Record which base-repository operations the installation token
   permits on the fork-sourced PR: read PR, label, comment, request
   changes, read head-branch contents.
2. Attempt a head-repository read via the installation token; record
   the exact failure (the App is not installed on the fork).
3. Record webhook deliveries for the fork PR lifecycle and which
   repository each names.
4. Record the config-fetch path: confirm effective config comes from
   the base default branch, never the fork (feeds 6.3 state 6).

## Observations

- **2026-07-23 — prerequisite probe (no fork needed).** Reading a repo
  the App is *not* installed on via the installation token returns
  **`404 Not Found` — not 403**: GitHub hides the repository's
  existence entirely. For the diagnostics catalogue this means
  "App not installed there" is indistinguishable from "repository does
  not exist," and *is* distinguishable from the permission-missing 403
  (which names the repo and the wanted grant). Predicts step 2's
  result for fork head-repos, to be confirmed against a real fork PR.
  Citation `2026-07-23T19-52-01-085Z#3`.
- **Blocked on setup (2026-07-23): the fork grid needs a second
  account.** Only `exploreriii` is authenticated, the sandbox has no
  forks, and it is currently **private** — so neither fork case exists
  yet. The runner (`harness/src/run-6.6.ts grid <pr> <public|private>`)
  is ready to execute the full step 1–4 grid the moment a fork-sourced
  PR exists. Setup needed, in order:
  1. private case: from a second account with collaborator access,
     fork the (private) sandbox and open a PR into it;
  2. public case: flip the sandbox to public, fork from the second
     account, open a PR — then run the grid for each.
- **2026-07-23 — public case complete** (the sandbox was flipped public
  and a second personal account opened PR #159; only the private
  column remains). Results:
  - **All base-repository operations work on a fork PR** exactly as on
    a same-repo PR: read, list files, label, comment, and an
    App-authored request-changes review all succeeded with the
    installation token. The App's moderation surface is unaffected by
    the fork origin.
  - **FINDING(fork-content-via-base-api).** The PR happened to add a
    file that exists *only* on the fork branch
    (`.github/.coderabbit.yml`) — and the **base** repository's
    Contents API serves it at the PR head sha (467 bytes), while the
    same path 404s on the default branch. Fork-authored content is
    therefore reachable through the base repo's own API surface: any
    config fetch that honors a PR-supplied ref reads
    contributor-controlled configuration. This is the concrete
    mechanism behind 6.3 state 6's rule — the effective-config fetch
    must pin the base default branch, never a ref that a PR can
    influence. It also generalizes: *anything* the platform fetches by
    a PR-derived sha (scripts, templates, policy files) is
    fork-controlled input and must be treated as such.
  - **Head-repo reads succeeded because the fork is public**, matching
    6.1's public-read result — the 404 wall demonstrated by the
    not-installed probe applies only to private repositories, which is
    what the private column must confirm.
  - **Delivery attribution is unambiguous.** Every delivery in the PR
    lifecycle (`pull_request.opened`, `.labeled`,
    `issue_comment.created`) names the **base** repository as
    `repository`; the fork appears only inside
    `pull_request.head.repo`. Routing on `repository.full_name` is
    safe for fork PRs.
  - **Gap noticed in passing:** the App-authored review generated no
    `pull_request_review` delivery — the throwaway App is not
    subscribed to that event. If a capability ever needs to observe
    reviews, the subscription list needs extending; recorded here so
    the permission ceiling review sees it.
  - The red line held: nothing from the fork was executed; all writes
    were labels/comments/reviews on the base PR.
