# 6.7 Read-after-write staleness (D46)

The recovery loop's exactly-once guarantee is proven relative to a consistent
read-back (register D46): a stale "absent" immediately after a landed write
makes the loop duplicate despite following every rule. This protocol measures
the actual staleness window on the reads the resolver uses, so the port's
freshness rule is a number, not a hope.

## Question

After a write returns success, how long until the corresponding LIST/read
endpoint reflects it — and in particular, how often is it visible on the very
first immediate read?

## Method

On a dedicated probe issue in the personal sandbox:

1. **Comment → list-comments** (the non-idempotent read-back path, the D46
   gate): create a comment carrying a unique marker, then immediately poll
   `GET /issues/{n}/comments` every ~150 ms until the marker is visible.
   Record write latency, lag-to-visible, poll count, and whether the FIRST
   immediate read saw it. 25 trials, 2 s pacing (well under the 6.4 secondary
   limit).
2. **Add-label → read issue** (the idempotent read-back / projection
   observation path): add a pre-created probe label, poll `GET /issues/{n}`
   until the label appears, remove it. 15 trials, same pacing.

All calls flow through the evidence Octokit; every response is a citable
record. Summary statistics (min / median / p95 / max lag, first-read hit
rate) land as a final observation record.

## What decides what

- First-read hit rate ≈ 100% and max lag ≈ 0 → the freshness rule can be
  "one immediate read suffices".
- Anything else → the rule becomes "delay D then re-read, N times" with D/N
  chosen above the observed p95/max, encoded in `executor/policy.ts` and the
  port; D46's register row records the measured basis.

Conclusion lands tracked in `design/operations/read-after-write.md`; the
endpoint matrix's affected rows gain a staleness note.
