# 6.8 Linked-issue semantics (D115)

`readLinkedIssues` is the one operation in `design/guides/adapter.md` with no
matrix row — a row without a citation is a guess, and this is the read the
`linkedIssues` resolver answers from. The audit found the existing bots answer
"what issue does this PR close?" two different ways that can disagree (B2), so
the question is not only whether GitHub answers it but which answer we adopt.
Until this runs, the resolver ships on an assumption.

## Question

For a pull request in the sandbox, what does GraphQL `closingIssuesReferences`
return — and how does it differ from what a maintainer would call a link?

## Method

On a personal sandbox repository, one probe pull request per case. Record the
raw response, the delivery or query id, and the quota headers for every call.

1. **Keyword close** — open a PR whose body says `Closes #N`. Query
   `closingIssuesReferences`. This is the baseline: it must return N.
2. **Manual mention** — a PR body that says `related to #N` and `see #N`, with
   no closing keyword. Record whether N appears. The audit's Inactivity Reaper
   used a body-text regex that would match these; the merge path used closing
   references, which would not (B2).
3. **Cross-repository** — a PR closing an issue in a second sandbox repository.
   Record whether it resolves, and whether the installation needs a grant it
   does not already hold.
4. **Multiple links** — one PR closing two issues; confirm ordering and that
   nothing is silently truncated.
5. **Edited after open** — open with no link, then edit the body to add
   `Closes #N`. Record whether the reference updates and how quickly, since
   the resolver reads at decision time, not at open time.
6. **Unlinked** — a PR with no references at all. Record the exact empty
   shape, so `absent` is distinguishable from a failure.
7. **Failure shapes** — repeat one query with a deliberately bad token, and
   once against a repository outside the installation. Record status, body
   pattern, and whether `classifyFailure` already covers them.
8. **Cost** — read `x-ratelimit-*` before and after the run, and record the
   GraphQL point cost per query against the Q10 budget.

## What decides what

- **Case 2 decides the platform's definition of a link.** If mentions do not
  appear, `linkedIssues` means "closing references only", the resolver's
  documentation says so plainly, and repositories wanting mention-based links
  need a configured alternative rather than a silent difference.
- **Case 3 decides the resolver's scope.** If cross-repository needs a grant
  outside the ceiling, the resolver is same-repository only until stage four
  reopens the ceiling.
- **Case 5 decides when the resolver may be memoized.** A reference that
  updates on edit cannot be cached across a delivery.
- **Cases 6 and 7 decide the fail-honest read.** `absent` and `unknown` must
  be different values; if their shapes are not distinguishable from the
  response, the adapter needs a rule that treats ambiguity as `unknown`.
- **Case 8 decides whether the sweep can afford it**, or whether the resolver
  is event-triggered only.

Conclusions land as rows in `design/findings/endpoint-permission-matrix.md`,
with the definition question recorded in the register. Only then does
`design/guides/adapter.md`'s blocked row become confirmed and the resolver
ship.
