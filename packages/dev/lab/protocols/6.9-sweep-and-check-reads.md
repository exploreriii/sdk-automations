# 6.9 Sweep and check reads

Six reads are implemented and, when this was written, none was cited. Three are
the ones `design/guides/sweep.md` §1 marked **needs a protocol**; two are the
resolver surface's own, refused for the same reason; one has no reader at all,
and this protocol chooses its endpoint. Until each had a row in the
endpoint-permission matrix the pull-request ladder was silent by `factsUnread`,
pr-quality showed three checks undetermined, and onboarding could not be built
at all.

**Run 2026-09-12 cited five of the six.** The sixth, `mergedCount`, was measured
on both candidates and decided on neither — see "Not decided by this protocol".

A read is confirmed here or it stays unread. Nothing below is settled by
reasoning about GitHub's documentation.

## Question

That the six reads the dormant ladders and checks need behave as their readers
already assume — payload shape, permission, one call per page, a free 304 on a
conditional read — and, for `mergedCount`, which of two endpoints is the honest
one.

| Read | Endpoint, as the reader spells it | What it wakes | Reader |
|---|---|---|---|
| `changesRequested` | `GET /repos/{o}/{r}/pulls/{n}/reviews` | inactivity's pull-request ladder, through the `review` fact group | `readChangesRequested` |
| `reapableSince` | `GET /repos/{o}/{r}/issues/{n}/timeline` (`ready_for_review`, `review_requested`, `convert_to_draft`) on a PULL REQUEST number | the same ladder | `readReapableSince` |
| `lastCommitAt` | `GET /repos/{o}/{r}/pulls/{n}/commits` | the same ladder — the only thing that resets a pull request's clock | `readLastCommitAt` |
| `commitAttestations` | `GET /repos/{o}/{r}/pulls/{n}/commits` (`verification`, `Signed-off-by:` in the message) | pr-quality's DCO and GPG checks | `readCommitAttestations` |
| `assigneesOf` | `GET /repos/{o}/{r}/issues/{n}` | pr-quality's assignment check | `readAssigneesOf` |
| `mergedCount` | undecided: `GET /search/issues?q=repo:…+is:pr+is:merged+author:…` against `GET /repos/{o}/{r}/pulls?state=closed` filtered | onboarding's whole welcome | none — the name is not in `RESOLVER_NAMES` |

`changesRequested` has two candidate reads in sweep.md §1 — GraphQL
`reviewDecision`, or the reviews list folded to each reviewer's latest deciding
state. `packages/runtime/src/adapter/reads/facts.ts` implements the second, so the
second is what this protocol measures. The first stays unprobed and unclaimed.

## Red line

**Reads only, with one exception: the setup's writes.** Every setup write is to
the personal sandbox, every one is reversible, and none is on a fork's head.
The App is given no `contents: write` for this protocol — the ceiling withholds
it deliberately — so any state that needs a branch or a commit is made by the
lead with their own credentials, the way protocol 6.3 wrote configuration
(`harness/put-config.sh`). Fork-authored content is never fetched at a
PR-derived ref (6.6).

No token, header or key is written anywhere. The evidence log keeps only the
harvested headers it already harvests.

## Method

### The state the sandbox must hold

| State | What it is | Made by |
|---|---|---|
| `PR_DRAFT` | a pull request opened as a draft | the seed, if it may create a branch; otherwise the lead |
| `PR_READY` | a pull request opened as a draft and since marked ready for review — the `ready_for_review` timeline event `reapableSince` folds | the seed (`markPullRequestReadyForReview`), on a branch it could create |
| `REVIEWER_LOGIN` | a login that may review here and is not the App | **the lead** — a second account is not something a token creates |
| `PR_REVIEW_REQUESTED` | a pull request with a review requested from `REVIEWER_LOGIN` | the seed, given that login |
| `PR_CHANGES_REQUESTED` | a HUMAN-authored pull request the App has requested changes on | **the lead names it**; the seed adds the review. GitHub refuses a review on one's own pull request, so the App cannot author both halves — protocol 6.6's PR #159 is exactly this shape |
| `PR_COMMITS` | a pull request whose head carries one GitHub-verified commit and one unsigned commit | **the lead.** A commit authored through the contents API is signed by GitHub and comes back `verification.verified: true`; an unsigned one needs a plain `git push` of a branch with a local unsigned commit. Both halves need `contents: write`, which the App does not hold |
| `MERGED_LOGIN` / `NEW_LOGIN` | a login with merged pull requests here, and one with none | **the lead** — merged history cannot be manufactured for a login the seed does not control |
| `ISSUE_ASSIGNED_MERGED` / `ISSUE_ASSIGNED_NEW` | one open issue assigned to each | the seed, given those logins |

Run 2026-09-12 used, in the personal sandbox `exploreriii/automation-sandbox`:
`PR_DRAFT` #179 · `PR_READY` #180, opened as a draft and since marked ready ·
`PR_REVIEW_REQUESTED` #181, from `cheese-cakee` · `PR_CHANGES_REQUESTED` #182,
the App's review · `PR_COMMITS` #183, carrying 8265874 (API-authored,
unverified), defc690 (pushed unsigned) and 1b12459 (GPG-signed, verified), all
three with `Signed-off-by` · `ISSUE_ASSIGNED_MERGED` #184 → `exploreriii` ·
`ISSUE_ASSIGNED_NEW` #185 → `aceppaluni`. All five pull requests were authored
by the lead through `gh`: the App holds `contents: read` and cannot create a
branch, which is the ceiling doing what the Red line says it does. Seed run
`2026-09-12T06-31-12-071Z`.

`harness/src/seed-6.9.ts` finds or makes every state it is allowed to make,
reads the installation's own grants rather than assuming them, and prints the
rest as a list for the lead with the reason it could not. `harness/src/run-6.9.ts`
reads that state back and creates nothing.

### How the calls are made

- **Five of the six reads are the platform's own readers**, imported from
  `packages/runtime/src/adapter/reads/facts.ts` and
  `packages/runtime/src/adapter/reads/resolvers.ts` and run over a client the harness
  implements. The URLs, the page walk and the folds under measurement are the
  ones that will ship. `mergedCount` has nothing to import, which is the point
  of its step.
- **Each request is sent once per step.** A retry would replace the failure
  shape the protocol exists to observe, which is also why the measured calls do
  not travel through Octokit: its throttling and retry plugins absorb exactly
  those signals (6.4).
- **Calls are paced two seconds apart**, well under 6.4's observed
  secondary-limit onset, and the run stops at the first unexpected failure,
  naming the step.
- **`--plan` resolves the environment and prints every step, its endpoint and
  the state it needs, without a single request.** The key file is reported as
  present or absent and never opened.

Evidence lands in `evidence/6.9-sweep-and-check-reads-<run>.jsonl`; the
citations below are ids in that ignored file.

## Steps

Every read step records the same six things: HTTP status; the permission named
by `x-accepted-github-permissions` on the negative control's 403; the
`x-ratelimit-used` delta across the step; whether an ETag came back and whether
a second conditional call returns 304; how many pages the reader actually
walked; and the value the reader folded.

| # | Step | Sends | What it adds |
|---|---|---|---|
| 1 | `state` | `GET /repos/{o}/{r}/pulls/{n}` per seeded pull request | reports what the seed left, and refuses the run naming the missing variable |
| 2 | `changesRequested` | the reviews list, through `readChangesRequested` | whether `COMMENTED` reviews are present and correctly ignored, and whether the fold sees one deciding state per reviewer |
| 3 | `reapableSince` | the pull request, then its timeline, through `readReapableSince` | **that a pull request number answers the issue timeline endpoint under the same grant** — the part no packet can assert for itself — and which mode events appear |
| 4 | `lastCommitAt` | the commits list, through `readLastCommitAt` | the commit date field's shape, and `null` against "no commits" |
| 5 | `commitAttestations` | the same commits list, through `readCommitAttestations` | that `verification.verified` is `true` on the API-authored commit and `false` on the pushed one, that `Signed-off-by:` is found, and that `parents.length > 1` marks a merge |
| 6 | `assigneesOf` | `GET /repos/{o}/{r}/issues/{n}`, through `readAssigneesOf` | that the single-issue endpoint is a different row from the confirmed LIST, and that assignees arrive whole and unpaged |
| 7 | `mergedCount` | **both** candidates, for both logins | `total_count` against the counted list; `incomplete_results`; the search API's separate budget (`x-ratelimit-resource: search`, and its own limit and remaining); the page count over the sandbox's closed pull requests |
| 8 | `negative` | the five reads again, on installation tokens minted without `pull_requests` and without `issues` | the permission each read actually needs, from the 403's `x-accepted-github-permissions` |

Step 8 is why the permission column can be filled at all. The harness has no
way to drop a permission at runtime — `harness/src/probe-permission.ts` calls an
endpoint outside the App's grant, which measures the ceiling and not one read's
floor. The mechanism is protocol 6.8's: mint a narrowed installation token and
re-issue the same read. The general 403 shape itself is not re-measured; it is
already in the failure catalogue from 6.1 and 6.4.

### What this run found

- **Every read is one call per page, every GET carries an ETag, and the second
  conditional call returned 304 with `x-ratelimit-used` unchanged** — the 304 is
  free, as the list-issues row already records.
- **The issue-timeline endpoint answers a pull-request number**, and does so
  with `pull_requests: read` alone or `issues: read` alone. The matrix's
  existing "Read issue timeline" row (Issues R) is broader than it states.
- **A commit authored through the contents API by a user token is NOT verified**
  (`reason: unsigned`); only the GPG-signed push was. A design that expects
  API-authored commits to be verified is wrong for user tokens.
- **`mergedCount`'s two candidates agreed on this sandbox**, and agreement does
  not decide it — see "Not decided by this protocol" below.

## What migrates

Conclusions never live here. A confirmed run moves:

**Four rows into the endpoint-permission matrix**, in the Operations table —
List PR reviews, Read item timeline on a pull-request number, List PR commits
(one row, two readers), and Read one issue. Each carries its permission from

**Five names into the two confirmation lists.** `changesRequested`,

`packages/runtime/src/adapter/reads/resolvers.ts`, which stops those two resolvers

Nothing about `mergedCount` migrates. See below.

## Not decided by this protocol

**Which endpoint answers `mergedCount`.** The step measured both and decides
neither, because the choice is not only about the numbers:

- The **search** endpoint answered in one call, but its index is eventually
  consistent, it reports `incomplete_results`, and it draws on a separate and
  much smaller budget (`x-ratelimit-resource: search`). A count that is
  sometimes low would welcome a returning contributor as a newcomer, which is
  the one mistake onboarding must not make.
- The **closed pull requests** list is exact and on the ordinary budget, but it
  cannot filter by author server-side, so its cost is the whole closed history
  divided by a hundred — per assignee, on every sweep. One page here, on a
  sandbox with almost no closed history.

The run's numbers are `search = 1` against `closed-pulls = 1` for `exploreriii`,
and `0` against `0` for `aceppaluni`: the two agree. Two numbers that agree do
not settle it — this sandbox is too small and too fresh to exercise either
endpoint's failure mode — and two that disagree would settle only that the
search index lagged on the day of the run. The decision needs a cost model
against the fleet budget (Q10) and a register row, and
`design/guides/capabilities/onboarding.md` phase 1 stays blocked until it has
one. Adding `mergedCount` to `RESOLVER_NAMES` before then would give a resolver
that is refused on the day it is added.

**Whether GraphQL `reviewDecision` is cheaper than the reviews list** is also
out of scope: the reader implements the list, and a second candidate with no
reader is a later question.
